# Skill admission

## Core rule

Treat a skill as a selectively loaded capability capsule, not a document about
a topic. Admit one only when it produces a meaningful behavior change on a
recurring, bounded task.

The compact shape combines a precise trigger, non-native delta, repeatable
guidance or resources, ownership, and evidence.

**Why:** every catalog entry spends eager description context and creates
another routing decision. Progressive disclosure reduces body cost, but it
does not make vague, generic, or overlapping entries free.

**How to apply:** run the test below before choosing a name, directory, or
description. Then use the [placement guide](placement.md).

## What earns a skill

* **Scoped operator context** - task-specific preferences or conventions.
* **Fast-moving domains** - retrieval procedures for knowledge newer than the model.
* **Beyond-model upskilling** - specialist methods, critique frameworks, or
  quality bars that demonstrably push results beyond generic model behavior.
* **Bespoke local truth** - custom tools, repository conventions, topology,
  deployment patterns, ownership, command routing, and local failure modes.
* **Repeatable workflows** - phases, questions, checkpoints, evidence
  requirements, stopping conditions, and output shapes for recurring work.
* **Tool adapters** - guidance and bundled resources that translate user intent
  into a custom command, API, file format, or operational surface.
* **High-cost mistake prevention** - narrow guidance for dangerous or expensive
  situations, including blast radius, recovery procedure, escalation points,
  and known traps.
* **Retrieval and navigation** - thin routers into deeper documentation,
  generated snapshots, runtime queries, or peer skills.

A category shows possible value, not automatic admission. The skill still
needs a precise trigger and an evaluated improvement.

## Reject or redirect

Reject a proposed skill, or move its content elsewhere, when it is:

* generic public knowledge with no local or specialist behavior delta
* a duplicate of `AGENTS.md`, command help, repository docs, or another skill
* a static copy of facts whose truth depends on the current date or live state
* a permission declaration that belongs in an authority system
* an invariant that code or a validator can enforce
* a one-off prompt with no recurring workflow
* a broad topic collection with no observable activation boundary
* scaffolding retained only for weaker models but exposed to every model

## Admission test

Answer every question before authoring:

1. **Gap** - What does an unassisted target model reliably get wrong or fail to
   know?
2. **Trigger** - What observable request or context should activate the skill?
3. **Delta** - What materially changes in the behavior or artifact?
4. **Recurrence** - Will the capability repeat often enough to deserve a name?
5. **Placement** - Why is this a skill instead of person context, `AGENTS.md`,
   docs, retrieval, tooling, validation, or authority configuration?
6. **Ownership** - Who maintains the source, and what event makes it stale?
7. **Evidence** - How will an author compare cold and skilled behavior and test
   routing precision?

If the answers are weak, stop authoring. Delete, merge, gate, or redirect the
material instead.

## Evidence and lifecycle

Record the owner and source of truth in or beside the skill. Test both routing
and task performance. Trigger checks catch descriptions that are vague or
over-broad. Cold-versus-skilled task checks prove that the body earns its
context cost.

Audit the catalog periodically for generic duplication, overlap, stale facts,
wrong audience, and model scaffolding that escaped its intended scope. Delete,
merge, or gate entries that no longer pass the admission test.
